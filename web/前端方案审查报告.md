# 前端方案专家审查报告

**审查对象**：`web/前端方案.md`（网页端前端与后端接口补充方案）  
**审查日期**：2026年5月12日  
**审查范围**：技术架构、API 设计、状态管理、安全性、用户体验、关键问题与实施优先级  
**重要约束**：历史记录不需要分页功能，本报告不将“历史记录缺少分页参数”列为问题。  
**审查结论**：**建议修改后实施**。方案整体方向清晰，技术栈选择合理，功能边界基本明确，可以作为网页端一期建设基础；但在 API 契约、状态类型、流式处理、安全边界和异常恢复策略方面仍需补充细化，否则实施阶段容易出现前后端联调成本高、流式消息状态混乱、Token 风险提示不足等问题。

## 一、审查结论

本方案能够覆盖网页端 C 与 Go 后端 B、扩展端 A 的主要交互场景，包括：

- 用户 HTTP API Token 配置；
- 在线工作区与扩展实例选择；
- 普通聊天请求；
- 流式聊天请求；
- 当前项目历史记录加载；
- 多语言支持；
- 基础错误提示和安全要求。

总体判断如下：

| 维度 | 结论 | 说明 |
|---|---|---|
| 技术架构 | 基本合理 | Vue 3 + Vite + TypeScript + Element Plus 适合当前场景，但目录结构还需增加类型、工具、常量等分层。 |
| API 设计 | 可用但需补充契约 | 端点设计基本清晰，但错误响应格式、SSE 事件结构、流式事件协议、鉴权失败处理需要统一。 |
| 状态管理 | 方向合理但偏粗 | 已区分认证、工作区、聊天状态，但缺少 Pinia 明确选型、核心类型定义、请求取消和多工作区消息键设计。 |
| 安全性 | 有意识但需强化 | 已提出 Token 脱敏、日志禁记 Token、历史记录主动加载等要求，但 localStorage 风险、XSS 防护、CORS 与请求头策略需细化。 |
| 用户体验 | 基础完整但交互细节不足 | 页面布局和主要交互明确，但流式滚动、错误恢复、离线状态、加载状态、取消请求等体验需补充。 |

**结论建议**：进入实施前，应先补齐“API 契约、类型定义、安全策略、流式协议与错误恢复策略”四类内容。完成这些补充后，可以按阶段推进前端开发。

## 三、API 设计评估

### 3.1 端点设计

方案列出的端点如下：

| 端点 | 方法 | 评估 |
|---|---:|---|
| `/api/me` | GET | 合理，用于 Token 校验和用户信息获取。 |
| `/api/workspaces` | GET | 合理，用于获取在线工作区和实例。 |
| `/api/workspaces/events` | GET | 合理，用于工作区状态变更推送；首版可轮询替代。 |
| `/api/chat` | POST | 合理，用于非流式聊天。 |
| `/api/chat/stream` | POST | 合理，用于流式聊天；需要明确事件协议。 |
| `/api/chat/history` | POST | 合理，用于主动加载当前项目历史记录。本报告不要求分页。 |
| `/health` | GET | 合理，用于健康检查。 |

端点整体符合当前业务动作模型。由于聊天请求天然包含复杂请求体，`POST /api/chat/history` 作为历史查询接口也可以接受。

### 3.2 RESTful 设计评价

方案并非严格资源型 RESTful，而是“资源端点 + 动作端点”的实用 API 风格。对于聊天、流式转发、历史读取这类后端代理扩展端的场景，这是可以接受的。

建议保持当前接口路径，但补充以下内容：

1. 每个接口的请求体结构；
2. 每个接口的成功响应结构；
3. 每个接口的错误响应结构；
4. 错误码枚举；
5. HTTP 状态码与业务错误码对应关系；
6. 流式接口的事件类型和数据格式。

### 3.3 响应格式需要统一

当前方案在 `/api/me` 和 `/api/workspaces` 示例中使用：

```json
{
  "ok": true,
  "payload": {},
  "error": null
}
```

但未完整定义错误响应格式。建议补充统一类型：

```ts
export type ApiResponse<T> = ApiSuccess<T> | ApiFailure;

export interface ApiSuccess<T> {
  ok: true;
  payload: T;
  error: null;
}

export interface ApiFailure {
  ok: false;
  payload: null;
  error: {
    code: string;
    message: string;
    detail?: string;
    requestId?: string;
  };
}
```

建议错误码至少包含：

```text
UNAUTHORIZED
FORBIDDEN
TOKEN_INVALID
WORKSPACE_NOT_FOUND
WORKSPACE_OFFLINE
INSTANCE_NOT_FOUND
REQUEST_TIMEOUT
RATE_LIMITED
CHAT_STREAM_ERROR
HISTORY_DISABLED
EXTENSION_ERROR
INTERNAL_ERROR
```

### 3.4 HTTP 状态码建议

| 场景 | HTTP 状态码 | 业务错误码 |
|---|---:|---|
| 未认证或 Token 无效 | 401 | `UNAUTHORIZED` / `TOKEN_INVALID` |
| 无权访问工作区 | 403 | `FORBIDDEN` |
| 工作区或实例不存在 | 404 | `WORKSPACE_NOT_FOUND` / `INSTANCE_NOT_FOUND` |
| 工作区离线 | 409 或 503 | `WORKSPACE_OFFLINE` |
| 请求超时 | 504 | `REQUEST_TIMEOUT` |
| 限流 | 429 | `RATE_LIMITED` |
| 历史记录未开启 | 409 | `HISTORY_DISABLED` |
| 扩展端错误 | 502 | `EXTENSION_ERROR` |
| 服务端内部错误 | 500 | `INTERNAL_ERROR` |

### 3.5 工作区 SSE 事件评估

`GET /api/workspaces/events` 的方向合理，但需要补充细节：

- 是否需要鉴权；
- 如何传递 Token；
- 心跳间隔；
- 重连策略；
- 事件 payload 完整结构；
- 前端收到断开事件后是否清理选中工作区。

浏览器原生 `EventSource` 不支持自定义 `Authorization` header。如果后端只接受 `Authorization: Bearer <token>`，则原生 EventSource 会受限。可选方案：

1. 首版不实现 SSE，使用 Axios 带 Authorization header 轮询 `/api/workspaces`；
2. SSE 使用短期一次性 token query 参数，例如 `/api/workspaces/events?access_token=...`，但需谨慎避免日志泄漏；
3. 改用 `fetch` + ReadableStream 自行消费 SSE，从而携带 Authorization header；
4. 若改为 cookie 鉴权，则需配套 CSRF 防护。

建议首版优先采用 **轮询 `/api/workspaces`**，降低鉴权和重连复杂度；SSE 作为二期优化。

### 3.6 聊天流式接口评估

方案已正确指出“Axios 浏览器端不适合直接消费 `text/event-stream`，建议 Fetch 读取流”。这是正确判断。

但仍需补充流式事件协议，例如：

```text
event: message_start
data: {"requestId":"...","messageId":"..."}

事件: content_delta
data: {"messageId":"...","delta":"..."}

事件: reasoning_delta
data: {"messageId":"...","delta":"..."}

事件: tool_call
data: {"messageId":"...","toolCall":{}}

事件: tool_result
data: {"messageId":"...","toolResult":{}}

事件: error
data: {"code":"EXTENSION_ERROR","message":"..."}

事件: done
data: {"messageId":"..."}
```

建议明确前端对每类事件的处理规则：追加正文、追加推理、更新工具调用、结束 loading、设置错误状态等。

### 3.7 历史记录接口说明

方案只要求“加载当前项目历史记录”，且关键约束明确历史记录不需要分页。因此，本报告不提出分页需求。

建议仅补充以下非分页契约：

- 请求体需包含当前工作区或实例标识；
- 返回消息应复用 `ChatMessage` 类型或提供可映射字段；
- 历史消息需标记来源，例如 `source: 'history'`；
- 历史加载应由用户主动点击触发；
- 历史记录未开启时返回明确错误码 `HISTORY_DISABLED`。

示例：

```ts
interface ChatHistoryRequest {
  workspaceId: string;
  instanceId?: string;
}

interface ChatHistoryPayload {
  messages: ChatMessage[];
}
```

## 四、状态管理评估

### 4.1 Store 模块划分

方案划分为认证、工作区、聊天三个状态模块，方向正确。建议增加设置模块：

| Store | 职责 |
|---|---|
| `auth` | Token、用户信息、登录状态、退出登录。 |
| `workspace` | 工作区列表、选中工作区、选中实例、在线状态、刷新/轮询状态。 |

### 4.2 认证状态

当前字段：

```text
apiToken
maskedToken
isLoggedIn
```

建议补充：

```ts
interface AuthState {
  apiToken: string | null;
  userId: number | string | null;
  isLoggedIn: boolean;
  validating: boolean;
  error: string | null;
}
```

`maskedToken` 可作为 getter，不建议作为持久状态存储：

```ts
const maskedToken = computed(() => maskToken(apiToken.value));
```

### 4.3 工作区状态

当前字段：

```text
workspaces

selectedInstanceId
loading
error
```

建议定义工作区类型：

```ts
interface WorkspaceInstance {
  workspaceId: string;
  instanceId: string;
  sessionId?: string;
  connectedAt?: string;
  lastSeenAt?: string;
  state: 'ready' | 'busy' | 'offline' | 'unknown';
  metadata?: {
    workspaceFolders?: string[];
    workspaceName?: string;
    [key: string]: unknown;
  };

```

建议补充：

- `lastRefreshAt`：最近刷新时间；
- `polling`：是否正在轮询；
- `selectedKey` getter：由 `workspaceId + instanceId` 组成；
- 多实例场景下的显示名称和排序规则。

### 4.4 聊天状态

当前字段：

```text
messagesByWorkspace
activeRequestId
streaming
historyLoading
error
```

建议重点补充消息结构：

```ts
interface ChatMessage {
  id: string;
  workspaceId: string;
  instanceId?: string;
  role: 'user' | 'assistant' | 'system' | 'tool';
  content: string;
  reasoning?: string;
  toolCalls?: ToolCall[];
  toolResults?: ToolResult[];
  createdAt: string;
  status: 'pending' | 'sending' | 'streaming' | 'done' | 'error' | 'cancelled';
  source: 'current' | 'history';
  error?: {
    code?: string;
    message: string;
  };
}
```

建议 `messagesByWorkspace` 的 key 不只使用 `workspaceId`，而使用组合 key：

```ts
const chatKey = `${workspaceId}:${instanceId ?? 'default'}`;
```

这样可以避免同一工作区多个扩展实例的消息相互覆盖。

### 4.5 请求取消机制

方案提到了“取消消息”，但未定义取消请求能力。建议为流式请求引入 `AbortController`：

```ts
interface ChatRuntimeState {
  activeRequestId: string | null;
  activeMessageId: string | null;
  abortController: AbortController | null;
  historyLoading: boolean;
  error: string | null;
}
```

用户切换工作区、退出登录、点击取消、路由离开时，应终止当前流式请求。

### 4.6 流式状态设计

`streaming` 可以保留作为全局运行态，但更推荐通过 `activeRequestId` 和消息 `status` 推导：

```ts
const isStreaming = computed(() => Boolean(activeRequestId.value));
```

如果允许多个工作区并发请求，则需要改为：

```ts
activeRequestsByWorkspace: Record<string, string>;
abortControllersByWorkspace: Record<string, AbortController>;
```

首版建议限制同一时间一个活动流式请求，降低复杂度。

## 五、安全性评估

### 5.1 Token 存储风险

方案明确：

- 网页端只保存 C 到 B 的 HTTP API Token；
- Token 默认保存在浏览器本地存储中；
- 展示时脱敏；
- 支持清除 Token；
- 保存前提示风险。

这些要求是必要的，但还需明确 localStorage 的风险：一旦页面存在 XSS，localStorage 中的 Token 可以被脚本读取。前端无法仅靠“本地加密”根治该风险，因为密钥通常也在前端。

建议表述为：

- Token 默认存储在 localStorage，属于便利优先方案；
- 保存前必须明确提示“请勿在公共电脑或不可信环境保存 Token”；
- 支持“仅本次会话保存”选项，使用 sessionStorage；
- 退出登录时必须清理 localStorage/sessionStorage 中的 Token 和用户信息；
- 不建议将 Base64 编码描述为加密；Base64 只能混淆，不能防护 XSS。

### 5.2 Token 脱敏规则

方案提出前四位和后四位展示。建议补充短 Token 的处理：

```ts
function maskToken(token: string): string {
  if (token.length <= 8) return '********';
  return `${token.slice(0, 4)}${'*'.repeat(Math.min(12, token.length - 8))}${token.slice(-4)}`;
}
```

### 5.3 请求安全

由于方案采用 `Authorization: Bearer <apiToken>`，不依赖 Cookie 自动携带认证信息，CSRF 风险相对较低。但仍建议补充：

- 生产环境必须使用 HTTPS；
- 后端 CORS 只允许可信前端源；
- 不允许 `Access-Control-Allow-Origin: *` 与敏感鉴权接口随意组合；
- 请求拦截器不得向第三方地址附加 Authorization；
- 失败重试时不得在日志中输出 Authorization 和聊天正文；
- 超时控制和取消控制应作为请求封装的一部分。

### 5.4 XSS 与内容展示安全

聊天消息可能包含模型输出、工具调用结果、历史记录内容，均应视为不可信输入。建议明确：

- 默认使用文本渲染，不使用 `v-html`；
- 如后续支持 Markdown，需要使用可信 Markdown 渲染器和 HTML sanitize；
- 工具调用参数和结果展示需要转义；
- 错误信息需要脱敏，不展示后端内部堆栈、Token、文件系统敏感路径等。

### 5.5 自动发送与历史记录安全

方案中“自动发送开关默认关闭”“历史记录按钮需要用户主动点击”是合理安全设计，应保留。

建议补充：

- 自动发送开启时给出显著状态提示；
- 发送前可选确认敏感内容；
- 历史记录加载结果默认只展示当前工作区/项目相关内容；
- 历史记录错误不应泄漏服务器日志路径或内部配置。

## 六、用户体验评估

### 6.1 页面布局

左右分栏符合工作区选择 + 聊天操作的使用场景。建议细化：

- 左侧栏固定宽度或可拖拽调整；
- 小屏幕下左侧栏可折叠；
- 右侧聊天区输入框固定在底部；
- 消息列表支持空状态、加载状态、错误状态；
- 工作区离线时在输入框上方显示原因和刷新按钮。

### 6.2 工作区选择体验

方案支持同一工作区多个实例选择，这是必要设计。建议补充：

- 工作区按在线状态、最近连接时间排序；
- 同一工作区多个实例时展示实例状态、sessionId 缩略值、lastSeenAt；
- 当前选中实例离线时，提示用户选择其他在线实例；
- 刷新列表时不要清空当前消息，仅更新工作区状态；
- 工作区为空时展示引导文案，例如“请先启动 VS Code 扩展端并保持在线”。

### 6.3 聊天消息展示

方案覆盖了用户消息、助手正文、推理片段、工具调用、工具结果、错误、取消和历史消息，类型完整。

建议补充展示规则：

| 消息类型 | 展示建议 |
|---|---|
| 用户消息 | 右侧气泡，显示发送中/失败状态。 |
| 助手正文 | 左侧气泡，支持流式追加。 |
| 推理片段 | 默认折叠，可全局开关和单条展开。 |
| 工具调用 | 使用可折叠卡片，显示工具名、参数摘要。 |
| 工具结果 | 默认折叠，长文本截断，可复制。 |
| 错误消息 | 红色提示，提供重试/复制错误信息按钮。 |
| 取消消息 | 中性提示，标识用户主动取消。 |
| 历史消息 | 使用轻量标记区分，例如“历史”。 |

### 6.4 流式输出体验

“支持流式追加正文”是核心能力，建议补充：

- 用户在底部附近时自动滚动到底部；
- 用户手动向上查看历史时暂停自动滚动，并显示“回到底部”按钮；
- 流式过程中显示停止/取消按钮；
- 流式结束后状态从 `streaming` 转为 `done`；
- 流式错误时保留已收到内容，并追加错误提示；
- 避免每个 token 都触发高频 DOM 更新，可按时间片或批量刷新。

### 6.5 输入框体验

方案定义了回车发送、组合键换行，建议进一步明确：

- Enter 发送，Shift+Enter 换行，或提供可配置项；
- 空内容不可发送；
- 请求中是否允许继续输入需明确；
- 未选择工作区、未登录、工作区离线时禁用并显示禁用原因；
- 发送失败后保留用户输入或保留失败消息，便于重试；
- 自动发送开关需要显著标识，避免误触发。

### 6.6 错误处理体验

方案列出了错误场景，但未定义恢复动作。建议补充：

| 错误 | 前端动作 |
|---|---|
| 未认证 | 清理本地 Token，跳转登录页。 |
| 工作区离线 | 禁用输入，提示刷新或选择其他实例。 |
| 请求超时 | 显示重试按钮，可重发上一条消息。 |
| 限流 | 显示稍后再试，并可展示冷却时间。 |
| 历史记录未开启 | 以普通提示展示，不作为致命错误。 |
| 扩展端错误 | 展示脱敏错误，可复制 requestId。 |
| 流式中断 | 保留已生成内容，标记为中断。 |

## 七、问题汇总

### 7.1 严重问题（必须修改）

| 编号 | 问题 | 影响 | 建议 |
|---:|---|---|---|
| S1 | API 错误响应格式未统一 | 前端难以在拦截器和页面层统一处理错误，联调成本高 | 定义 `ApiSuccess` / `ApiFailure` / 错误码 / HTTP 状态码映射。 |
| S2 | 流式聊天事件协议未明确 | 前端无法稳定解析正文、推理、工具调用、错误和结束事件 | 明确 SSE 或流式文本事件类型、payload 结构和前端状态转换规则。 |
| S3 | Token 存储安全边界描述不足 | 用户可能误以为 localStorage 足够安全，XSS 场景下存在泄漏风险 | 明确风险提示、sessionStorage 选项、退出清理、禁止将 Base64 称为加密。 |
| S4 | 核心类型定义缺失 | TypeScript 难以发挥作用，消息、工作区和 API 数据结构容易漂移 | 增加 `types/api.ts`、`types/chat.ts`、`types/workspace.ts` 等。 |

### 7.2 一般问题（建议修改）

| 编号 | 问题 | 影响 | 建议 |
|---:|---|---|---|
| M1 | 未明确状态管理库 | 实施时 Store 写法可能不统一 | 明确使用 Pinia，并定义各 Store 职责。 |
| M2 | `messagesByWorkspace` key 设计不够细 | 同一工作区多个实例时消息可能混淆 | 使用 `workspaceId:instanceId` 组合作为消息 key。 |
| M3 | 缺少请求取消机制 | 用户无法停止流式输出，切换页面可能残留请求 | 使用 `AbortController` 管理流式请求。 |
| M4 | SSE 鉴权方式未明确 | 原生 EventSource 不能设置 Authorization header，实施可能受阻 | 首版采用轮询；若使用 SSE，明确 fetch stream 或鉴权替代方案。 |
| M5 | 工作区状态枚举不完整 | ready/offline/busy 等状态在 UI 表达上可能不一致 | 定义统一 `WorkspaceState` 枚举。 |
| M6 | 路由守卫策略偏简略 | Token 失效、刷新页面、已登录访问登录页等场景处理不清 | 补充启动时 token 校验、401 拦截跳转、默认重定向。 |
| M7 | 错误恢复策略不足 | 用户遇到失败后不知道如何继续 | 为每类错误定义重试、刷新、跳转、忽略等动作。 |

## 九、总体评价

这份前端方案已经具备较好的业务覆盖度和可实施基础，尤其是以下点值得肯定：

- 明确了网页端 Token 与扩展端 WebSocket Token 的区别；
- 页面结构符合“工作区选择 + 聊天面板”的核心使用路径；
- 技术栈选择主流且适合当前项目；
- 正确识别 Axios 不适合浏览器端直接消费流式 SSE，建议使用 Fetch；
- 对 Token 脱敏、日志禁记 Token、历史记录主动加载、自动发送默认关闭等安全点已有基本意识；
- 考虑了多语言和工作区在线状态变化。

主要不足集中在“方案从功能描述到工程契约”的距离仍较大：API 错误格式、流式事件、类型定义、状态转换、安全边界和异常恢复需要更明确。若直接进入编码，前端实现可能依赖开发者临场约定，后期容易出现联调返工。

**最终建议**：  
本方案可以作为一期网页端建设的基础方案，但应在实施前完成第一阶段补充，尤其是 API 契约、流式协议、核心类型和 Token 安全策略。历史记录功能按当前约束处理为“用户主动加载当前项目历史记录”，无需分页设计，也不应将缺少分页作为问题。
